# 提案：把 Gemtek XR1710G 纳入 wrt_release 构建体系

- 状态：**提案（Proposal），未执行**
- 日期：2026-11-06
- 范围：只讨论结构、边界和实施步骤，不包含任何代码或配置改动
- 前置：XR1710G 的设备支持由独立仓库维护，相关需求在另一个工作流中提交

---

## 1. 摘要

把 Gemtek XR1710G（Airoha AN7581）纳入 `kaiwater/wrt_release` 时，**不复制设备树和驱动**，而是把现有 fork 继续作为"系统/硬件上游"，`wrt_release` 只负责应用层和发布层。

目标形态：

```text
ImmortalWrt-for-Gemtek-brightspeed @ naoki66-base
    = 系统/硬件上游（DTS、image、kernel、驱动、feed patches）
                │  作为 REPO_URL
                ▼
wrt_release
    = 应用层（compile_base + fragments）+ 发布层（release identity）
```

现有 `naoki66-base` 已经把应用层拆到 `custom/config.fragment`，这个边界可以复用，不需要重新设计。

---

## 2. 背景

### 2.1 设备

| 项目 | 值 |
|---|---|
| 型号 | Gemtek XR1710G（`gemtek,xr1710g`） |
| 平台 | `airoha/an7581`，AN7581GT |
| 内存 / 闪存 | 2 GiB / 512 MiB NAND |
| 无线 | MT7996AV 三频 Wi-Fi 7 |
| 有线 | 2×10G RTL8261BE + 2×1G |
| 其他 | NCT7802 PWM 风扇、NPU、PON（XG2010G 变体） |

设备当前运行社区版 immortalwrt，**不在本仓库的构建体系内**，也没有 `/etc/wrt_release`。

### 2.2 上游分支现状

`kaiwater/ImmortalWrt-for-Gemtek-brightspeed` 的 `naoki66-base` 是完整的 immortalwrt fork，已具备：

| 路径 | 作用 |
|---|---|
| `1710.config` | 完整设备配置（9385 行，409 个 `=y` 包） |
| `custom/config.fragment` | **纯应用层**，注释里明确写明 hardware 包不在此处 |
| `custom/files/` | rootfs 覆盖（apk mirror、channel_analysis.js） |
| `patches/feeds/` | luci / packages 补丁（dawn 6GHz、msd_lite、vlmcsd） |
| `scripts/apply-feed-patches.sh` | 应用上述补丁 |
| `scripts/set-build-version.sh` | 版本号前缀 |
| `feeds.conf.default` | 额外 feed：`app_airoha`、`pon_drivers`、`onu_config`、`easytier`、`bandix`、`helloworld`、`pushbot` |
| `target/linux/airoha/` | XR1710G DTS、image recipe、board.d、风扇、PON、NPU |
| `.github/workflows/` | 自带构建与上游同步（`sync-upstream.yml`） |

### 2.3 `1710.config` 的构成

按包名粗分：

```text
系统相关（kmod / firmware / airoha / npu / i2c / fan / base / luci-base）：约 205
应用相关（luci-app / 代理 / 工具类）：约 204
```

也就是说，直接把 `1710.config` 当 `BASE_CONFIG` 会把约 204 个应用选择一起带进来，需要过滤或拆分。

## 3. 目标与非目标

### 目标

1. XR1710G 可以由 `wrt_release` 统一构建、发布、带 `/etc/wrt_release`
2. 应用规划与现有设备（AP8220 / AX6600 / BE12 Pro）共用 `compile_base` + fragments
3. 设备支持继续由 fork 维护，`wrt_release` 不复制 DTS / image / 驱动
4. 两侧都能独立构建、独立维护

### 非目标

- 不把 XR1710G 的硬件补丁搬进 `wrt_release`
- 不在本提案中执行合并
- 不处理 XG2010G / PON 变体（后续单独立项）
- 不改变现有三个型号的配置

---

## 4. 分层设计

### 4.1 系统层（留在 base）

| 类别 | 内容 | 归属理由 |
|---|---|---|
| 设备树 | `target/linux/airoha/dts/an7581-xr1710g.dts` | 硬件相关 |
| 镜像 | `target/linux/airoha/image/an7581.mk` 中的 `gemtek_xr1710g` | 分区/布局相关 |
| board.d | LED、网络、风扇、PON、默认配置 | 板级初始化 |
| 内核 | 6.18.x、airoha 补丁 | 平台相关 |
| 固件 | `airoha-en7581-*-firmware`、`rtl826x-firmware` | 硬件 |
| 硬件工具 | `i2c-tools`、NCT7802 fan、`luci-app-airoha` | 板级 |
| feed 补丁 | `patches/feeds/**` | 与设备/无线行为绑定 |
| 额外 feed | `app_airoha`、`pon_drivers`、`onu_config` | 硬件相关 |

### 4.2 应用层（放进 wrt_release）

| 类别 | 内容 |
|---|---|
| 代理 | `proxy` fragment（PassWall + sing-box） |
| 应用 | `compile_base.config` + 设备 fragments |
| 发布 | `/etc/wrt_release`、`DISTRIB_BUILD_*`、默认 LAN / WiFi |
| 精简策略 | `light_apps`（按需，512M 闪存的设备可用） |

### 4.3 边界规则

1. base 不新增应用选择，除 standalone 构建用的 `custom/config.fragment`
2. `wrt_release` 不新增设备补丁
3. 应用取舍以 `wrt_release` 为唯一事实来源
4. base 的 `custom/config.fragment` 仅服务 base 自身构建，`wrt_release` 不读取

## 5. 实施步骤（分阶段，均未执行）

### Phase 0：决策与前置确认

| 事项 | 需要确认的内容 |
|---|---|
| 应用取舍 | base 的 `ddns-go` / `rtp2httpd` / `bandix` 与现有 `istorex` / `pbr` / `adguardhome` / OAF 如何取舍 |
| OAF 可行性 | `kmod-oaf` 能否在 `6.18.55 + airoha/an7581` 编译并加载 |
| U-Boot 布局 | 设备当前是 0x700000 布局还是 UBI 布局；base 只构建前者 |
| 应用规划稳定性 | 近期 `wrt_release` 应用层仍在调整（iStore/lucky/xray 精简、geodata 策略），需等稳定后再接入 |

**验收**：以上四项有明确结论，否则不进入 Phase 1。

### Phase 1：新增 model 骨架

新增文件：

```text
wrt_core/compilecfg/gemtek_xr1710g_immwrt.ini
wrt_core/deconfig/gemtek_xr1710g_immwrt.config
```

`ini` 草案：

```ini
REPO_URL=https://github.com/kaiwater/ImmortalWrt-for-Gemtek-brightspeed.git
REPO_BRANCH=naoki66-base
BUILD_DIR=airoha-xr1710g
CONFIG_FRAGMENTS=proxy
# COMMIT_HASH=<pin 到具体提交>
```

`deconfig` 只放 target / device / 系统项：

```text
CONFIG_TARGET_airoha=y
CONFIG_TARGET_airoha_an7581=y
CONFIG_TARGET_MULTI_PROFILE=y
CONFIG_TARGET_DEVICE_airoha_an7581_DEVICE_gemtek_xr1710g=y
CONFIG_TARGET_DEVICE_PACKAGES_airoha_an7581_DEVICE_gemtek_xr1710g=""
```

**验收**：`./build.sh gemtek_xr1710g_immwrt config_preview` 通过。

### Phase 2：base layer 适配模块

新增模块（建议 `wrt_core/modules/base_layer.sh`），全部按"存在才执行"处理，不影响其他上游：

| 步骤 | 触发条件 | 说明 |
|---|---|---|
| 应用 feed 补丁 | `$BUILD_DIR/scripts/apply-feed-patches.sh` 存在 | `FEED_PATCHES_STRICT=1` 执行 |
| 复制 rootfs 覆盖 | `$BUILD_DIR/custom/files` 存在 | 复制到 `$BUILD_DIR/files/` |
| 移除 `pushbot` feed | `feeds.conf` 含该条目 | 避免 `feeds update` 解析失败 |
| 去重 `dae/daed` | 存在重复 feed | 避免包冲突 |
| 跳过 base 应用片段 | 始终 | `custom/config.fragment` 不由本仓库读取 |

**验收**：非 airoha 模型的构建流程与产物不变。

### Phase 3：系统配置收敛

两条路线，建议先用 A 再演进到 B：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | `BASE_CONFIG=1710.config` + `BASE_CONFIG_FILTER` | 快，保留全部系统项 | 需维护过滤列表，应用选择易混入 |
| B | base 侧新增 `xr1710g-system.config`（去掉应用层），`wrt_release` 指向它 | 边界最干净 | 需要改 base 仓库 |

推荐最终形态：**B**。系统知识留在 base，应用知识留在 `wrt_release`。

**验收**：合并后的配置中，系统符号与 `1710.config` 一致，应用符号完全由 `wrt_release` 决定。

### Phase 4：构建与设备验证

构建验证：

- `config_preview` 顺序正确
- 系统包无缺失（kmod / firmware / NPU / fan）
- OAF（如启用）编译通过
- 镜像包含 `/etc/wrt_release`、LAN `192.168.50.1/24`、默认 WiFi

设备验证（刷机前必须确认 bootloader 布局）：

- 启动、网络、2.4/5/6 GHz
- 风扇转速与温度读数
- 10G 网口
- PassWall + sing-box 基本连通
- `/etc/ssl/certs/ca-certificates.crt` 为 120 个证书（CA 黑名单生效）
- rootfs 无 `geoip.dat` / `geosite.dat`

## 7. 可维护性规则

1. **单一职责**：base = 硬件/系统，wrt_release = 应用/发布
2. **不复制设备支持**：`wrt_release` 不出现 XR1710G 的 DTS、image recipe、驱动补丁
3. **不扩散应用选择**：base 不新增应用包，`custom/config.fragment` 只服务 standalone 构建
4. **pin 提交**：`COMMIT_HASH` 固定 base 版本，避免上游同步影响发布可复现性
5. **同步节奏**：base 用现有 `sync-upstream.yml` 跟随 immortalwrt；`wrt_release` 只在 kernel/target 变化时调整 deconfig
6. **变更记录**：两边各自维护 changelog，跨仓库变更在 `wrt_release` 的 changelog 中引用 base 提交

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| OAF 在 airoha/6.18 无法编译 | 应用规划缺项 | Phase 0 先做编译验证；失败则不启用 OAF |
| U-Boot 布局不匹配 | 刷机变砖 | 刷机前用 `cat /proc/mtd` / 现场确认；只构建匹配布局 |
| feeds 冲突（pushbot、dae） | 构建早期失败 | base layer 模块显式清理 |
| 应用规划仍在变动 | 多层改动叠加出错 | 等 `wrt_release` 应用层稳定后再进入 Phase 1 |
| 内核 6.18 与现有补丁不兼容 | 构建失败 | 现有模块大多有存在性判断，需实际跑一遍确认 |
| base 与 wrt_release 应用选择漂移 | 维护混乱 | 明确以 `wrt_release` 为准，base fragment 不参与本仓库构建 |
